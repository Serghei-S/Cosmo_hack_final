# Синтетические данные для контроля качества

## Основной расширенный набор v2

Актуальный набор для развития интерфейса и сквозной демонстрации находится в `expanded_dataset/`: **180 изделий, 1 955 уникальных событий, 2 065 доставок, 110 точных повторов, 30 некорректных доставок в отдельной очереди и 18 связанных фото**. Набор содержит обычное прохождение линии, разные приоритеты сигналов CV, ремонтопригодные дефекты, несколько неустранимых случаев, слабые/потерянные кадры, действия мастера, решения контролёра, заключения технолога, поздние сообщения и пропущенные необязательные сведения.

```powershell
python quality_dataset/generate_expanded.py
python quality_dataset/validate_expanded.py
python quality_dataset/replay_ingest.py
python quality_dataset/package_data.py
```

Генератор также воспроизводит прежний малый набор `dataset/` с 12 изделиями — он оставлен для регрессионных проверок и отдельного сквозного ERP-эмулятора. JSON-файлы расширенного набора воспроизводимы при каждом запуске. Восемнадцать уже сохранённых синтетических изображений лежат в `media/`; их хеши проверяются валидатором. Генератор не вызывает сервис генерации изображений. `replay_ingest.py` — независимый эталон проверки входа: он принимает 1 955 событий, исключает 110 точных дублей и отправляет 30 ошибочных сообщений в карантин.

У послеоперационных событий контроля версии 2.0 есть `media_evidence.before_operation` и `media_evidence.after_operation`: ссылки и SHA-256 для доступных файлов, либо `url: null`, пустой хеш и причина отсутствия. Входной контроль хранит собственный кадр в `evidence_refs`; парное сравнение появляется после операции. `defects` содержит оценку длины и ширины в мм, класс дефекта и `depth_estimated_mm` (обычно `null`). Это **синтетические оценки CV**, а не поверенный замер. `kd_spec` содержит учебный класс зоны, условный предел длины **риски** и ссылку `КД-ДЕМО-*`; реальные нормативы предприятия не заявляются. Состояние изделия (`item_state`) фиксирует физическую локацию и блокировку линии на момент каждого события; интерфейс берёт последнее принятое состояние.

Для отсутствующего файла `sha256_hash` остаётся строкой `""`: действительный хеш нельзя вычислить из не переданных байтов. `CLASSIFIED_RESTRICTED` означает учебное предположение, что внешнему интерфейсу доступен только структурированный результат из закрытого контура; это не утверждение о действующей политике конкретного предприятия.

## Малый контрольный набор v1

Это полностью вымышленный, воспроизводимый набор данных для кейса «Интеллектуальный контроль качества деталей в космической отрасли». Он показывает путь изделия от задания ERP-эмулятора до контроля, решения человека и результата для внешней системы. Никакие параметры, допуски, сотрудники, изделия и показатели не взяты с реального производства.

## Быстрый запуск

Нужен Python 3.10+; дополнительные пакеты и аккаунты внешних систем не требуются.

```powershell
python quality_dataset/generate.py
python quality_dataset/validate.py
```

`generate.py` создаёт файлы в `quality_dataset/dataset/` с одинаковым содержимым при каждом запуске. `validate.py` проверяет связи, хронологию, повторы, решения, расчёты, интеграционные сообщения и контроль целостности. Строки в `events/deliveries.jsonl` отсортированы по **времени доставки**, поэтому файл можно воспроизводить последовательно. Время возникновения события может быть более ранним.

Для живой демонстрации используйте `events/source_deliveries.jsonl` как поток от внешних источников и выполняйте решения человека через интерфейс. `interactions/scripted_actions.jsonl` содержит сценарий этих действий для автоматических проверок. Полный `events/deliveries.jsonl` объединяет оба потока и подходит для регрессионного воспроизведения. Так решение контролёра не подставляется системой компьютерного зрения.

## Производственная история

Условное изделие — кронштейн приборного блока. Экземпляр состоит из корпуса, вставки и двух крепёжных элементов. Линия включает входной контроль, механическую обработку и сборку. На производственных участках работают два оператора в разные смены. Контролёр качества и технолог представлены отдельными ролями. Все имена и ID условные.

| Изделие | Что происходит | Что должно получиться |
| --- | --- | --- |
| `ITEM-001`, `002` | Нормальный путь через входной контроль, обработку и сборку. | Полная история, годный финальный контроль. |
| `ITEM-003` | Финальное наблюдение плохого качества; затем ручная проверка. | До ручной проверки годность не подтверждается. |
| `ITEM-004` | Вмятина обнаружена на входе, до операций. | Подтверждённый входной брак; оператор обработки не связан с его возникновением. |
| `ITEM-005` | Хороший входной контроль и царапина после обработки. | Подтверждённый дефект, известен интервал появления; конкретная причина не доказана. |
| `ITEM-006` | Входное состояние оценить невозможно, после обработки видна царапина. | Дефект подтверждён, момент возникновения неизвестен. |
| `ITEM-007` | Во время обработки предупреждение станка; после неё два разных признака дефектов в одном сигнале. | Один бракованный экземпляр, два случая дефекта; связь со станком остаётся гипотезой. |
| `ITEM-008` | Один заусенец замечен дважды, подтверждён, затем выполнена повторная обработка и ручная проверка. | Один исторический случай дефекта; отдельный повторный запуск операции и допуск после него. |
| `ITEM-009` | Слабый сигнал о царапине, ручная проверка её не подтверждает. | Отклонённое наблюдение, без подтверждённого брака. |
| `ITEM-010` | Входное наблюдение поступает после сигнала с обработки; сам сигнал доставки повторён. | Хронология восстанавливается по времени события, а повтор не удваивает счётчики. |
| `ITEM-011` | Зафиксирован и подтверждён пропуск обязательного действия; дефекта не обнаружено. | Подтверждённая процедурная ошибка учитывается отдельно от дефектов и причин брака. |
| `ITEM-012` | Обработка началась и остановлена на паузу. | Незавершённая операция без выдуманной длительности и без итогового результата ERP. |

Три нормальных изделия и несколько сопоставимых операций дают базу для сравнения времени работы. Размер набора выбран для понятной защиты; для нагрузки в дальнейшем можно размножать эти истории с новыми идентификаторами, сохраняя причинные связи и правила проверки.

Для нагрузки уже есть отдельный генератор:

```powershell
python quality_dataset/generate_load.py --copies 20 --spacing-seconds 30 --source-replicas 3
```

Он создаёт `quality_dataset/load_dataset/` с 240 изделиями, 1880 уникальными событиями и 1900 доставками. `--spacing-seconds` управляет плотностью потока, а `--source-replicas` — количеством независимых экземпляров каждого типа источника. ID изделия, компонентов, выполнений операций, событий и ссылок в решениях меняются согласованно. Нагрузочный файл содержит только события и справочник изделий; интеграционный обмен проверяется на малом основном наборе. Путь вывода можно задать через `--output`.

## Как читать события

Каждая строка основного файла имеет два уровня:

```json
{
  "delivery_id": "DLV-0001",
  "deliver_at": "2026-02-17T08:01:00+03:00",
  "message": {
    "event_id": "EVT-0001",
    "event_type": "item_received",
    "schema_version": "1.0",
    "occurred_at": "2026-02-17T08:00:00+03:00",
    "source_id": "MES-EMU",
    "item_id": "ITEM-001",
    "item_type_id": "TYPE-BRACKET-01",
    "line_id": "LINE-01",
    "station_id": "ST-IN",
    "shift_id": "SHIFT-A",
    "data": {"work_order_id": "WO-A", "assembly_revision": "A", "component_ids": ["..."]}
  }
}
```

`message` — содержимое сигнала источника. `delivery_id` и `deliver_at` — параметры тестового транспорта. Принимающее приложение самостоятельно фиксирует своё `received_at`; время доставки из файла помогает воспроизвести задержку. Повтор может иметь новый `delivery_id`, но прежний `event_id` и **точно такое же сообщение**. Два сообщения с одним `event_id`, но разным содержимым, должны отправляться на разбор как конфликт.

Версия схемы сообщения (`schema_version`) отделена от версии внешнего анализатора (`analyzer_version`). `operation_run_id` обозначает конкретное выполнение операции. При доработке создаётся новый ID со ссылкой на прежний. Длительность, переданная MES-эмулятором, явно помечена как полное время на участке в минутах (`elapsed_station_time`), а не активное время резания.

Результат контроля принимает ровно три состояния: `signs_detected`, `no_signs_detected`, `unable_to_assess`. Качество наблюдения и уверенность — отдельные поля. Пустой `evidence_refs` означает отсутствие фото и видео. Это не пропущенное доказательство и не изображение-заглушка.

## Правила интерпретации для MVP

1. **Наблюдение и решение различаются.** Сигнал с `signs_detected` создаёт признак несоответствия, а `quality_decision` подтверждает либо отклоняет его. Решение содержит автора, основание и ссылку на исходное наблюдение. Исходный сигнал не меняется.
2. **Несколько наблюдений могут относиться к одному дефекту.** Для этого набора их связывает сочетание `item_id + component_id + defect_type_id + region` в пределах одного жизненного цикла дефекта. Два наблюдения заусенца у `ITEM-008` образуют один случай. Для реального производства правило потребуется уточнить при наличии двух независимых дефектов одного типа в одной зоне.
3. **Дефект и изделие с дефектом считаются отдельно.** У `ITEM-007` два подтверждённых дефекта, но это одно изделие с браком. Повторная доставка и доработка не создают новый исторический случай.
4. **Причина имеет самостоятельный статус.** Предупреждение станка, совпавшее по времени с дефектом, даёт гипотезу. Дефект после операции не доказывает ошибку оператора. Подтверждённое процедурное нарушение у `ITEM-011` не становится причиной несуществующего дефекта.
5. **Неопределённость сохраняется.** `unable_to_assess` и плохое наблюдение не подтверждают годность. При отсутствии качественного состояния до операции место возникновения дефекта остаётся неизвестным.
6. **Позднее событие перестраивает представление, сохраняя историю получения.** Порядок доставки и порядок возникновения не совпадают у `ITEM-010`. Проверка после пересчёта должна давать один случай дефекта.
7. **Исправления только добавляются.** Ручное решение, доработка и последующий допуск — новые записи. Историческое подтверждение дефекта не исчезает после успешной доработки.

## Интеграция и дополнительные проверки

Задания `WO-A` и `WO-B` должны попасть в приложение до событий соответствующих изделий. Ожидаемые исходящие сообщения содержат `correlation_key`: ERP-эмулятор использует его, чтобы повторное получение не создало вторую запись. Для `ITEM-007` первая отправка получает `temporary_unavailable`, следующая — `accepted`. У `ITEM-012` итогового сообщения нет: операция ещё не закончена.

Некорректные сообщения находятся только в `invalid_deliveries.jsonl`: отсутствующее обязательное поле, неизвестная версия, неизвестное значение результата, неизвестное изделие, противоречащий дубль и завершение без ID выполнения операции. Для них ожидается изоляция с кодом ошибки, без изменения основной истории. Версия 1.0 преднамеренно фиксирована; правила для будущего совместимого расширения следует проверять при введении версии 1.1.

`integrity/baseline.json` даёт воспроизводимый эталон хешей и последовательной цепочки. `tamper_case.json` меняет решение контролёра в копии события; `validate.py` проверяет, что хеш перестал совпадать. Это **демонстрация обнаружения изменения**, не промышленная защита от администратора, который может переписать и события, и эталон. Для целевой системы контрольную точку следует подписывать и хранить отдельно от изменяемой базы.

Целевые профили интеграций описывают также предполагаемый технический интерфейс. Для 1С предусмотрены опубликованный [OData-интерфейс](https://v8.1c.ru/platforma/rest-interfeys/) или [HTTP-сервис](https://v8.1c.ru/platforma/http-servisy/); для Галактика:ERP — веб-сервис либо [адаптер шины](https://galaktika.ru/esb) при наличии соответствующего компонента; для КОМПАС-3D — адаптер через [SDK/API](https://help.ascon.ru/KOMPAS/24/ru-RU/sdk_inform.html). Способ обмена с установленной MES остаётся проектным предположением. Проверка каждого настоящего подключения потребует доступа к конкретной конфигурации заказчика.

## Что сознательно остаётся предположением

Индекс вибрации, его предел, типы дефектов, состав изделия, времена операций, качество сигналов и решения специалистов созданы для сценария. Они не являются измеренными допусками космического производства. Здесь нет реальных изображений, CV-модели, геометрии КОМПАС-3D, действующих ERP/MES и персональных данных. Перед применением на предприятии потребуется проверить идентификацию изделий, правила группировки дефектов, единицы измерения, часы источников и производственные процедуры вместе с заказчиком.
