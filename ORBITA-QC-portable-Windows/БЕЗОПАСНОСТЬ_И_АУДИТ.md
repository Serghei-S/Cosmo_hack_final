# Информационная безопасность и аудит ОРБИТА.QC

Этот контур отвечает на технический критерий 3 (шина безопасности, критические действия, журнал и права) и пункты 2 «Защита» и 3.4 постановки (исходная история, шифрование, отдельные ключи, контроль целостности). Проверяемый код: `security.mjs`, `security-crypto.mjs`, серверный вызов шины в `server.mjs`, браузерный клиент `source/src/security-client.ts` и `source/tests/security.test.mjs`.

| Требование организаторов | Реализация и способ проверки |
| --- | --- |
| Шина безопасности | Каждый API-запрос проходит через `security.handle` или `security.guard`; неизвестные маршруты закрываются. Тест проверяет `401`, `403`, CSRF и чужую линию. |
| Разграничение прав | Серверная матрица ролей, область линий, учётные сеансы; интерфейс роли сам по себе не даёт права вызова. |
| Критические действия | Разрешение действия и точный результат пишутся двумя новыми записями с серверным автором, причиной и идентификатором. Сервер проверяет порядок событий, тип, решение, статус, основание и принадлежность линии. |
| Неизменяемый журнал | Зашифрованные записи только добавляются, связаны HMAC-цепочкой и подписанным указателем конца. Тест меняет запись и усекает файл; дальнейшая работа останавливается. |
| Шифрование и ключи | Состояние ERP/MES/CAD и полезная нагрузка аудита шифруются AES-256-GCM, ключ выводится из отдельного локального файла и не включается в архив. |
| Защита API-контрактов | Входящие JSON-запросы ограничены по типу содержимого, размеру, глубине и числу ключей. События, доставки, решения, ERP/MES и MobileOps проверяются по локальным JSON Schema; лишние поля и ключи прототипа отклоняются. |

## Где проходит граница доверия

Браузерный выбор роли и `localStorage` не считаются удостоверением личности. Локальная демонстрация на `127.0.0.1` открывает рабочее место без формы входа: `/api/security/demo-session` создаёт сеанс выбранной роли. Это удобство демонстрации, а не защита от другого пользователя того же компьютера. Маршрут отключён при явно заданном списке пользователей. При запуске переносимого сервера создаётся локальный 256-битный ключ вне Git и ZIP. Из него выводятся независимые ключи для шифрования данных, шифрования аудита и контрольной цепочки.

Сервер выдаёт случайный сеанс в `HttpOnly; SameSite=Strict` cookie. JavaScript получает только отдельный CSRF-токен в памяти. На локальном HTTP `Secure` для cookie не выставляется; при выносе сервера за `127.0.0.1` требуется HTTPS и cookie с `Secure`, а открытый выбор ролей должен быть отключён. Сеанс живёт не более 8 часов и закрывается после 30 минут бездействия. При переключении роли прежний сеанс удаляется. Администратор видит активные сеансы и может отозвать чужой сеанс. Отдельный API входа с паролем остаётся для конфигурации с явно заданными пользователями и проверяется тестами.

Шина перед каждым изменяющим API-запросом выполняет: **сеанс → CSRF и Origin → право по роли → проверка целостности аудита → запись попытки → обработчик**. Неизвестный маршрут закрыт по умолчанию. Действие по изделию дополнительно проверяет принадлежность линии. Автор события берётся из серверного сеанса, а не из поля формы. Сервер сравнивает присланные события с разрешённым действием: типы и их порядок, точный идентификатор, решение, статус, основание, линия и учётная запись. Серверное подтверждение действия и его исходные события сохраняются отдельно от браузерной проекции. При входе браузер сверяет действия роли с подтверждёнными сервером событиями и удаляет неподтверждённые локальные записи `ORBITA-UI`. Переносимый HTTP-сервер добавляет CSP, запрет фреймов и ограничения доступа к ресурсам браузера.

| Учётная роль | Разрешённые критические действия |
| --- | --- |
| Контролёр | Подтвердить или отклонить признак, назначить доппроверку, решить о списании, повторном контроле и выпуске; передать подтверждённое решение в MES |
| Мастер | Зафиксировать выполнение/очную проверку на доступной линии |
| Технолог | Заключение о доработке, гипотеза и установленная причина |
| Руководитель | Чтение разрешённых данных, без записи решений и настроек |
| Администратор | Получение и отправка ERP-сообщений, импорт сборок, повторы обмена, просмотр и проверка аудита |

Шлюз MES получает факты для открытого рабочего места и возвращает только события разрешённых линий. Полные журналы ERP и MES доступны администратору; рабочие места получают только признак настройки MES. Шлюз принимает исходящее решение только тогда, когда его точное содержимое совпадает с завершённым действием контролёра в серверном журнале. Серверные состояния ERP и MES/CAD записываются как `AES-256-GCM` конверты. Старый открытый JSON демообмена автоматически переносится в зашифрованный формат при первом чтении. Повреждённый зашифрованный конверт не принимается.

Контракты из `contracts/` загружаются при старте сервера и не могут ссылаться на сетевые ресурсы. Общий JSON-парсер до бизнес-логики требует `application/json`, ограничивает размер тела, глубину вложенности и число ключей, отклоняет массив вместо объекта и ключи `__proto__`, `prototype`, `constructor`. Схемы запрещают неизвестные поля, задают пределы строк и массивов и проверяют идентификаторы и даты. Полученные и сформированные сервером сообщения проверяются перед сохранением, постановкой в очередь или отправкой. `cd source; pnpm contracts:check` проверяет встроенный поток и интеграционные примеры, а `pnpm test` включает отрицательные сценарии с лишними и опасными полями. Это снижает риск массового присваивания, загрязнения прототипа и незаметного дрейфа формата, но не заменяет TLS, WAF и лимиты на уровне промышленного reverse proxy.

## Журнал и контроль вмешательства

`data/security/audit.jsonl` содержит только зашифрованные полезные нагрузки. Для каждой записи есть номер, MAC предыдущей записи и собственный `HMAC-SHA-256`; отдельный подписанный контрольный указатель обнаруживает усечение конца журнала. Перед критической операцией цепочка проверяется. При нарушении сервер останавливает изменение и выдаёт ошибку. В журнале остаются входы, неудачные попытки входа, отказы в правах, разрешения и завершения действий, обращения к изменяющим API-маршрутам. Старые записи приложением не переписываются.

Это **логическая неизменяемость и обнаружение вмешательства**. Пользователь с правами изменения файлов и ключа на том же компьютере способен уничтожить оба артефакта; физическую неизменяемость обеспечит внешняя WORM-копия или удалённый независимый журнал. Для производства нужны отдельное хранение ключа (HSM/секрет-хранилище ОС), TLS, общая транзакционная база событий, резервирование, срок хранения и проверка восстановления. Учебные исходные данные в репозитории синтетические и открытые; `localStorage` остаётся кэшем представления и сценарием воспроизведения, а не защищённым хранилищем. Валидные данные, намеренно введённые уполномоченным оператором, журнал атрибутирует, но не доказывает их фактическую достоверность.

## Резервирование и восстановление

«Безопасность → Резервирование» создаёт ZIP в `data/backups/`. В архив входят текущий корневой ключ, аудит, контрольная точка и зашифрованные состояния; старые комплекты восстановления ключа исключаются. Для каждого файла манифест содержит размер и SHA-256. После записи сервер распаковывает архив в отдельную временную папку, сверяет путь, CRC32, размер и SHA-256 каждого файла и только затем помечает копию проверенной. Создание и успешная проверка записываются в аудит.

Архив содержит ключ, поэтому его нужно переносить в отдельное защищённое хранилище и ограничивать доступ. В промышленном контуре ключ и копию данных следует хранить раздельно, а восстановление выполнять по утверждённому регламенту. Потеря ключа делает зашифрованные данные недоступными.

## Ротация и автоматические проверки

Корневой ключ меняется только при остановленном сервере командой `cd source; pnpm security:rotate -- --confirm`. Скрипт проверяет старый аудит, расшифровывает состояния, сохраняет комплект восстановления, создаёт новый ключ, полностью пересобирает защищённый журнал и повторно проверяет все новые конверты. Отпечатки старого и нового ключей и результат операции остаются в журнале и локальных метаданных; учебные пароли меняются вместе с ключом.

Workflow `.github/workflows/quality-gate.yml` при push и pull request проверяет контракты, тесты, отсутствие `data/`, ключей и `.env` в Git, известные уязвимости зависимостей, production-сборку, CycloneDX SBOM и Windows-архив.

## Как показать жюри

1. Запустить `START.cmd`, выбрать роль контролёра и записать решение с основанием. Автор берётся из сеанса выбранной демороли.
2. Переключить роль на администратора, открыть «Безопасность → Аудит действий» и нажать «Проверить целостность». В журнале видны выбор роли, решение и связанные контрольные значения.
3. Запустить `cd source; node --test tests/security.test.mjs`. Тест в отдельной временной папке проверяет `401/403`, CSRF, запрет чужой роли и линии, атрибуцию автора, шифрование состояния, изменение записи и усечение журнала. Он не повреждает рабочий журнал демонстрации.
4. Открыть `data/integration-state.json` после обмена ERP: вместо исходного заказа там зашифрованный конверт. Папка `data/` исключена из Git и переносимого ZIP.

Основание для выбора проверок: [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).
