# Развёртывание и эксплуатация

## Проверка состояния

```sh
docker compose ps
docker compose logs --tail 100 api emulator
docker compose exec -T db psql -U orbita_owner -d orbita -c 'SELECT destination,status,count(*) FROM outbox GROUP BY destination,status;'
```

Логи API содержат ID запроса, маршрут и причину ошибки, без тела пароля или содержимого фотографии. Отказ команды не подтверждает её выполнение. Сначала сверяйте журнал и ключ идемпотентности. Статусы `pending`, `sending`, `retry_wait`, `accepted`, `failed` различаются явно. В административной диагностике можно повторно поставить ошибочное сообщение в очередь; уже принятое сообщение не отправляется как новое решение.

Внутренний `/metrics` предоставляет счётчики запросов, ошибок, активных запросов и uptime. Для централизованного мониторинга собирайте их из закрытой сети с доверенным CA. Рекомендуемые сигналы: возраст старейшей очереди, число failed, ошибки журналов, заполнение диска, длительность транзакций, запас соединений. Полный OpenTelemetry collector и система оповещений в Compose не установлены.

## Резервная копия и восстановление

В рабочем месте администратора «Резервные копии» создаётся JSON-снимок. Основная БД читается в `REPEATABLE READ READ ONLY`, перед сохранением проверяются цепочки. Медиа неизменяемы и добавляются отдельно; копия может включать ещё не привязанный файл. Сеансы и счётчики ограничений не переносятся. Копия содержит зашифрованные payload, индексы, квитанции и outbox, но **не ключи**.

Сразу перенесите копию и записанный SHA-256 в независимое защищённое хранилище. Keyring резервируется отдельно с ограниченным доступом. Потеря старой версии ключа делает соответствующие записи нечитаемыми. Для больших объёмов используйте PostgreSQL backup/PITR: JSON-снимок рассчитан на проверяемый локальный стенд и загружается в память.

Проверка восстановления на Windows создаёт две временные БД, восстанавливает копию, проверяет цепочки и SHA-256 фотографий, затем удаляет **только эти временные БД**:

```powershell
pwsh -File deployment/verify-restore.ps1 -BackupFile "$PWD/.runtime/backups/<backup-id>.json"
```

Сам восстановитель отказывается писать в непустые таблицы. Для переноса на новую площадку подготовьте пустые БД с миграцией `001_core.sql`, задайте `DB_NAME` и `MEDIA_DB_NAME`, монтируйте исходный keyring и копию, передайте заранее сохранённый хеш:

```sh
docker compose run --rm --no-deps \
  -e DB_NAME=orbita_recovery -e MEDIA_DB_NAME=orbita_recovery \
  -e BACKUP_SHA256=<sha256> \
  api node server/restore.mjs --restore-empty /backups/<backup-id>.json
```

Не направляйте пользователей на восстановленные БД до успешной проверки. Две БД восстанавливаются последовательно; при сбое используйте новые пустые цели. Перед включением работников очереди сверяйте подтверждения внешней ERP: доставка имеет семантику at-least-once и требует идемпотентного получателя.

## Ключи

Оперативное шифрование использует версионированный keyring. Ротация меняет ключ новых записей; старые оригиналы не переписываются. Старые ключи сохраняются для чтения и проверки HMAC.

```sh
docker compose stop api emulator
node app/source/scripts/rotate-keyring.mjs .secrets/keyring.json
docker compose up -d --no-build --force-recreate --scale api=2
```

Скрипт создаёт копию keyring перед атомарной заменой. Обновите права чтения для UID контейнера согласно политике хоста; не делайте секреты доступными другим пользователям. На Linux каталог `.secrets` имеет права 0700. Смена ключа шифрования не изменяет пользовательские пароли. Сертификаты и ключ подписи руководителя имеют отдельный жизненный цикл.

CA private key и owner-пароли БД не монтируются в API или веб-сервис. На предприятии замените файловые секреты Vault/KMS/HSM либо секретами оркестратора. Копия одной DB без независимого keyring и без процедуры восстановления не считается достаточным резервом.

## Гибридный архив

`hybrid-crypto.mjs` использует нативный Node.js 24.14 crypto: X25519 и ML-KEM-768, объединение секретов HKDF и AES-GCM. Заголовок с профилем, key ID и source ID аутентифицируется. Приватные ключи получателя не входят в envelope. CLI описывает аргументы при запуске без команды:

```sh
node app/source/scripts/archive-crypto.mjs
```

Профиль применяется отдельно от оперативной БД. Для миграции сохраняйте исходный envelope внутри нового архивного объекта и ссылку на его source ID; не заменяйте оригинальные производственные записи. Тесты проверяют чтение после смены активного ключа, отсутствие старого ключа, изменение AAD/tag и сохранение ссылки при переносе. Это не сертифицированный криптомодуль.

## Подключение шлюзов

Compose по умолчанию запускает собственный ERP-эмулятор. Для реального адаптера задайте переменные из документов `app/ERP_АДАПТЕРЫ.md` и `app/MES_КОМПАС_АДАПТЕРЫ.md` в отдельном override, смонтируйте mapping и секреты. Файлы с паролями/токенами не коммитятся. Проверяется сертификат шлюза, HTTP для удалённого адреса отклоняется. Начните с приёмочного заказа и тестового результата; сверьте внешнюю квитанцию и внутреннюю историю.

Внутренние ID должны быть устойчивыми. Неизвестное изделие/компонент/версия отправляются в ошибку приёма. Подготовку номенклатуры и каталогов выполняют до открытия линии. Редактирование фикстуры после первоначального импорта само по себе не меняет существующую БД.

## Изменение правил и источника анализа

Версия анализатора и версия схемы сохраняются в каждом исходном сообщении. Внешняя CV-модель не обучается приложением. Изменения допуска и распознавания проходят согласование: зафиксировать исходный набор, разметку и версию; проверить на независимых случаях с пропусками и ложными сигналами; сравнить показатели с действующей версией; получить утверждение ответственного; включить ограниченный участок; сохранить старую конфигурацию для отката. Исторические записи остаются привязанными к прежней версии. При откате меняются новые поступления, исходные события не переписываются.

Изменение схемы сопровождается обновлением контракта, регенерацией и проверкой дрейфа. База первой версии создаётся миграцией при пустом volume. Новые миграции применяются в согласованное окно обслуживания отдельной административной ролью; runtime API не получает права изменения схемы.

## Приёмка площадки

До производственного запуска закрепите реальные допуски, утверждённые маршруты, полномочия пользователей, IDs, синхронизацию часов, сроки хранения и правомерность работы с изображениями. Замените сценарные ограничения на нормативы площадки. Проверяйте пиковый поток, длительный прогон, потерю экземпляра API, восстановление DB, недоступность ERP и потерю подтверждения, а также восстановление с отдельного носителя. Зафиксируйте RPO/RTO и измеренный SLO. Число контейнеров без этих испытаний не является доказательством готовности к заданной нагрузке.

## Остановка экземпляра API

Nginx разрешает переход к другому API при ошибке соединения, тайм-ауте и HTTP 502/503, максимум две попытки. Повтор отправленного `POST` не включён: директива `non_idempotent` не используется, согласно [документации Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream). Уже начатую передачу ответа автоматически восстановить нельзя; клиент обновляет состояние перед повторным решением.

После исчерпания попыток доставки сообщение остаётся `failed` и блокирует более поздние сообщения того же изделия и получателя. Администратор устраняет причину и использует «Повторить». Исходное решение и история ошибок не удаляются.
