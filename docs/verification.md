Проверки выполнены 26 сентября 2026 UTC / в ночь на 27 сентября по Москве на локальном Docker Desktop. Рабочий каталог расположен на диске A. ## Измерение HTTP

Два экземпляра API, по 2 CPU и 1,5 ГБ RAM, пул до 12 соединений на каждую БД; Nginx перед ними. 100 запросов, параллелизм 10, один локальный клиент.

| Сценарий | HTTP 200 | p50 | p95 | Максимум | Общее время |
| --- | ---: | ---: | ---: | ---: | ---: |
| Получение полной истории после изменения курсора | 100/100 | 891 мс | 3942 мс | 6525 мс | 13,34 с |
| Опрос с неизменившимся курсором | 100/100 | 32 мс | 126 мс | 264 мс | 0,456 с |

Первая строка измеряет передачу и расшифрование истории; вторая — короткий ответ `unchanged`. Эти величины нельзя смешивать. Тест показывает пользу курсора и работоспособность двух API, но не доказывает линейный рост производительности или готовность к миллионам событий. Длительный прогон, сравнение одного/нескольких узлов, потеря хоста и SLO площадки не выполнялись в финальном сокращённом цикле проверок.

## Повторение

Из корня проекта после запуска Docker:

```sh
docker compose exec -T api node --test server/tests/database.test.mjs server/tests/crypto.test.mjs
docker compose exec -T api node scripts/verify-outbox.mjs
```

```powershell
$env:TEST_CA_FILE = "$PWD/.secrets/ca.crt"
node app/source/scripts/smoke-production.mjs
# Необязательный короткий HTTP-прогон:
$env:LOAD_REQUESTS = '100'
$env:LOAD_CONCURRENCY = '10'
node app/source/scripts/smoke-production.mjs
```

Для генерации отдельных наборов с разным числом источников и плотностью событий:

```sh
python quality_dataset/generate_load.py --copies 100 --source-replicas 4 --spacing-seconds 1 --output .runtime/load-dataset
```

Генератор создаёт отдельные справочники и события; новые ID требуют импорта согласованной номенклатуры. Его выход нельзя загружать в рабочую БД без подготовки её каталогов. Сценарии одного и нескольких API запускаются параметром `--scale api=1` / `--scale api=2`. Отказы шлюза, повтор квитанции и восстановление буфера проверяются протокольными тестами, а не отключением производственного оборудования.

## Контракты и автоматизация

`pnpm contracts:generate` запускает `orbita-contracts/1.0.0`, `pnpm contracts:check` проверяет результат. Источники генерируемого кода: схема производственного события и `workflow-policy.json`. Выход: `src/generated/contracts.ts` и `server/contracts.generated.mjs`.

Пример согласованного изменения — исключение `tech_allow`/`tech_deny` из политики технолога. Серверная карта прав и тип команды обновляются одной генерацией; забытая генерация приводит к ошибке проверки. Неизвестная версия, лишнее поле ERP-квитанции и неверная структура сообщения обнаруживаются валидатором до применения. Тесты шлюзов проверяют преобразование статусов, включая отдельные `REWORK` и `SCRAP`.

`.github/workflows/quality-gate.yml` содержит воспроизводимый workflow для совместимого Actions runner. Факт запуска удалённого CI в GitVerse не заявляется: команды quality gate выполнены локально, настройки runner зависят от размещения репозитория.

## Визуальная проверка и ограничения

Пользователь подтвердил открытие HTTPS сайта в Edge и Chrome. Встроенный браузер автоматизации оставался на предупреждении локального CA; автоматизированный полный проход интерфейса не заявляется. В README включены реальные сохранённые снимки интерфейса контролёра и руководителя. Они показывают синтетический сценарий и состояние на момент съёмки.

Реальные 1С, Галактика, MES, КОМПАС и робот в среде отсутствуют. Проверены наши адаптеры и эмуляторы; присоединение продуктов предприятия требует согласованных шлюзов и реквизитов. Нормативы, сценарные ограничения, месячная сводка и фотографии демонстрационного набора должны быть заменены данными площадки перед промышленным вводом. Одноузловой Compose не обеспечивает HA БД и входного балансировщика.
