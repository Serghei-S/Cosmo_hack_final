# MES и КОМПАС-3D: границы интеграции

В `plant-integrations.mjs` реализованы два независимых контура: двусторонний обмен с согласованным шлюзом MES и запрос структуры сборки у локального адаптера КОМПАС-3D. Оба контура проверены на HTTP-стендах. Установленные MES и КОМПАС-3D в этой поставке отсутствуют; их собственные API ещё не испытаны.

## MES без повторного ручного ввода

Источник фактов операции — MES; источник решения ОТК — ОРБИТА.QC. Серверный worker раз в 5 секунд выполняет синхронизацию независимо от открытого браузера: сервер забирает пакет событий MES по курсору, сопоставляет внешние ID и сохраняет оригиналы. Новые события автоматически попадают в хронологию изделия через существующий приёмник событий. Когда контролёр записывает решение в паспорте, оно без второй формы попадает в серверную очередь и отправляется в MES. Журнал в разделе «Центр интеграций → MES без повторного ввода» показывает поступившие факты, квитанции и ошибки.

Шлюз MES должен предоставлять:

- `GET /events?after={cursor}` → `{ "cursor": "CURSOR-2", "events": [...] }`. Курсор должен обозначать устойчивую позицию в журнале MES. Он обновляется только после проверки и сохранения **всего** пакета. Повтор одного `eventId` с тем же содержимым не создаёт второй факт; изменение содержания при прежнем ID — ошибка.
- Для событий допустимы `operation_started`, `operation_finished`, `operation_paused`, `operator_action`, `machine_state`. Пример: `{"eventId":"E-1","type":"operation_started","occurredAt":"2026-02-17T16:05:00+03:00","itemKey":"MES-UNIT-007","itemTypeKey":"MES-TYPE-BRACKET-01","lineKey":"MES-LINE-01","stationKey":"MES-ST-MILL","shiftKey":"MES-SHIFT-B","runKey":"MES-RUN-007-1","operationKey":"MES-OP-MILL","actorKey":"MES-OPERATOR-02","equipmentKey":"MES-CNC-01","data":{}}`.
- `POST /quality-status` принимает `{ "eventId", "itemKey", "decision", "disposition", "occurredAt", "actorId", "findingRefs" }` и возвращает `{ "eventId", "status": "accepted|retry|rejected", "receiptId", "errorCode" }`. Повтор того же `eventId` должен вернуть прежний результат без повторного проведения действия.

Настройка сервера: `ORBITA_MES_BASE_URL`, при необходимости `ORBITA_MES_TOKEN`, и `ORBITA_MES_MAPPING_FILE`. Пример словарей внутренних и внешних ID лежит в `source/integration-fixtures/mes-mapping.example.json`. Нужны изделия, типы, линии, участки, смены, запуски, операции, исполнители и оборудование. Неизвестный ID отклоняется, вместо подстановки по похожему названию.

Сетевые ошибки, HTTP 429/5xx и квитанция `retry` сохраняются и повторяются с тем же `eventId` до пяти автоматических попыток. Явный отказ `rejected` остаётся в журнале для разбора. Запросы к удалённому шлюзу требуют HTTPS; локальный `127.0.0.1` может использовать HTTP. В Docker состояние адаптера хранится как зашифрованный документ PostgreSQL с логическим ключом `plant-integration-state.json`.

Решение ОТК, аудит и outbox фиксируются одной транзакцией. Worker отправляет только сохранённый оригинал решения; при вызове адаптера проверяется совпадение всего сообщения с историей. Курсор и блокировка синхронизации общие для реплик. Очередь Docker имеет до восьми попыток, после ошибки администратор выполняет ручной повтор. Более поздние решения того же изделия не обгоняют необработанное сообщение.

## Прямой запрос структуры КОМПАС-3D

В интерфейсе «КОМПАС и сборки» добавлена команда «Получить через адаптер». Сервер обращается к локальному CAD-адаптеру по `GET /assemblies/{assemblyId}`, проверяет дерево компонентов и импортирует его в тот же журнал версий, что и резервный JSON-файл. Повтор ревизии не создаёт вторую сборку; другой состав под тем же номером ревизии отклоняется. Геометрия **не импортируется** и всегда отмечается `geometry_included: false`.

Ожидаемый ответ адаптера:

```json
{
  "assemblyId": "KOMPAS-ASM-BRACKET-01",
  "itemTypeId": "KOMPAS-TYPE-BRACKET-01",
  "revision": "B",
  "components": [
    { "instanceId": "BODY-1", "typeId": "KOMPAS-BODY", "parentInstanceId": "KOMPAS-ASM-BRACKET-01", "quantity": 1 },
    { "instanceId": "INSERT-1", "typeId": "KOMPAS-INSERT", "parentInstanceId": "BODY-1", "quantity": 1 }
  ]
}
```

Сервер проверяет уникальность экземпляров, родителей, циклы, типы и количество. Внешние обозначения типов переводятся через `ORBITA_KOMPAS_MAPPING_FILE`; пример — `source/integration-fixtures/kompas-mapping.example.json`. Адрес и токен адаптера: `ORBITA_KOMPAS_BASE_URL`, `ORBITA_KOMPAS_TOKEN`.

На компьютере с КОМПАС-3D потребуется небольшой SDK-процесс, который откроет документ сборки, прочитает её верхний компонент и рекурсивно обойдёт вложенные компоненты, определит обозначения, ревизию и количество вхождений, затем выдаст этот JSON. Выбор объектов и признаков исключения нужно согласовать с используемой версией КОМПАС и правилами предприятия. Официальный SDK поставляется с КОМПАС-3D; его документация описывает [IKompasDocument3D](https://help.ascon.ru/KOMPAS_SDK/24/ru-RU/ksapi_ikompasdocument3d_methods.html) и [обход `TopPart → Parts`](https://help.ascon.ru/KOMPAS_SDK/23/ru-RU/iparts7.html). Сам SDK-процесс в этой поставке не реализован и не проверен без установленного КОМПАС-3D. Реализованы серверный запрос к нему, преобразование, проверка и запись сборки.

## Проверка

`cd source; pnpm test` поднимает локальные шлюзы MES и CAD и проверяет курсор, повторы, несопоставленный ID, автоматическую очередь решения, квитанции, дерево сборки, конфликт ревизии и отсутствие геометрии. Это проверка контрактов и нашего кода, а не реального оборудования или САПР.
