# Адаптеры 1С и «Галактика:ERP»

ОРБИТА.QC содержит два отдельных серверных адаптера в `erp-adapters.mjs`. Они проверены сквозными тестами на локальных HTTP-стендах. Подключение к конкретной установленной ERP пока не проверялось: конфигурация 1С и интерфейс «Галактики» у заказчика неизвестны. Описанные ниже маршруты и поля — **предлагаемый контракт интеграционного шлюза**, а не обещание, что типовая поставка ERP выдаёт их без настройки.

## Граница и ответственность

- Выбирается **одна** ERP как источник заказов, номенклатуры и серийных номеров. ОРБИТА.QC отвечает за решение по качеству. Профили 1С и «Галактики» альтернативны.
- ОРБИТА.QC запрашивает заказ по внутреннему ID, адаптер переводит его во внешний ключ и получает JSON от ERP. После проверки и сопоставления ID сервер сохраняет нормализованный заказ.
- Результат контроля отправляется по тому же заказу и серийному номеру. Ключ `correlation_key` остаётся неизменным при повторе. ERP-шлюз должен по этому ключу возвращать прежнюю квитанцию без повторного проведения документа.
- Логический ключ состояния для каждого профиля отдельный: `data/integration-state-1c.json` и `data/integration-state-galaktika.json`. Демонстрационный эмулятор продолжает использовать `data/integration-state.json`. Смешивать состояния профилей запрещено.
- В зашифрованном документе состояния сохраняется исходный ответ ERP для разбора обмена; браузер получает только нормализованное задание и внешние ключи. Docker сохраняет состояние в PostgreSQL через `source/server/adapters.mjs`; доступ к административному API проверяется сервером.
- Ни токен, ни пароль не передаются браузеру и не записываются в журнал обмена. Удалённый шлюз допускается только по HTTPS; HTTP допускается на loopback-адресе.

## Включение профиля

Задайте переменные в `services.api.environment` отдельного Compose override. Имена `data/*.json` обозначают ключи совместимого адаптера; в Docker отдельные файлы состояния не создаются.

| Переменная | Значение |
| --- | --- |
| `ORBITA_ERP_PROFILE` | `emulator` (по умолчанию), `1c` или `galaktika` |
| `ORBITA_ERP_MAPPING_FILE` | Путь к JSON-файлу сопоставления ID; относительный путь считается от папки `app` |
| `ORBITA_1C_BASE_URL` | Корневой адрес опубликованного HTTP-сервиса 1С |
| `ORBITA_1C_USER`, `ORBITA_1C_PASSWORD` | Учётная запись для Basic Auth, если её требует шлюз 1С |
| `ORBITA_1C_TOKEN` | Альтернатива Basic Auth: Bearer-токен |
| `ORBITA_GALAKTIKA_BASE_URL` | Корневой адрес согласованного шлюза «Галактики» |
| `ORBITA_GALAKTIKA_USER`, `ORBITA_GALAKTIKA_PASSWORD` | Basic Auth, если его требует шлюз |
| `ORBITA_GALAKTIKA_TOKEN` | Альтернатива Basic Auth: Bearer-токен |

Пример override (URL заменяется адресом согласованного шлюза):

```yaml
services:
  api:
    environment:
      ORBITA_ERP_PROFILE: 1c
      ORBITA_1C_BASE_URL: https://erp-gateway.example.internal
      ORBITA_ERP_MAPPING_FILE: /run/config/erp-mapping.json
    volumes:
      - ./deployment/erp-mapping.json:/run/config/erp-mapping.json:ro
```

Запуск: `docker compose -f compose.yaml -f compose.erp.yaml up -d --no-build --scale api=2`. Токен или Basic Auth передаются через защищённую конфигурацию окружения оркестратора. Файл с реальными реквизитами не включается в Git.

Файл примера содержит условные внешние ключи; замените их ключами тестовой базы. В нём задаются три словаря **внутренний ID → внешний ID**: `orders`, `itemTypes`, `items`. Внешние ключи должны быть уникальны в каждом словаре. Если ERP прислала неизвестный заказ, тип изделия или серийный номер, импорт отклоняется с HTTP 422; догадка по совпадению строк не используется.

Для «Галактики» укажите `galaktika`, `ORBITA_GALAKTIKA_BASE_URL` и `source/integration-fixtures/erp-mapping-galaktika.example.json`.

## Контракт шлюза 1С

Предлагается опубликовать в конфигурации или расширении 1С HTTP-сервис. Названия внутренних документов и полей базы заказчика сопоставляются **внутри 1С** с этим внешним контрактом. Текущий адаптер не использует и не изменяет типовые объекты 1С напрямую.

`GET /orbita/orders/{order_ref}` → HTTP 200:

```json
{
  "order_ref": "1C-REF-WO-B",
  "number": "WO-B",
  "product_code": "1C-CODE-BRACKET-01",
  "assembly_revision": "A",
  "serial_numbers": ["1C-SERIAL-007"],
  "modified_at": "2026-02-17T15:45:00+03:00"
}
```

`POST /orbita/quality-results` получает JSON с `message_id`, `idempotency_key`, `order_ref`, `serial_number`, `verdict_code`, `evidence_event_ids`. Коды решения: `ACCEPT`, `HOLD`, `RELEASE_AFTER_REWORK`, `REWORK`, `SCRAP`. Ответ HTTP 200:

```json
{
  "idempotency_key": "QC-...",
  "status": "ACCEPTED",
  "receipt_id": "1C-ACK-123",
  "error_code": null
}
```

Для временного отказа шлюз возвращает `status: "RETRY"`, для окончательного отказа — `status: "REJECTED"` и код ошибки. Ключ в квитанции обязан совпадать с отправленным.

## Контракт шлюза «Галактика:ERP»

Точный механизм доступа зависит от установки заказчика: веб-сервис, интеграционная шина или отдельный шлюз. Адаптер ожидает следующий JSON-контракт:

`GET /integration/work-orders/{documentId}` → HTTP 200:

```json
{
  "documentId": "GAL-DOC-WO-B",
  "documentNo": "WO-B",
  "sku": "GAL-SKU-BRACKET-01",
  "specRevision": "A",
  "units": [{"serialId": "GAL-UNIT-007"}],
  "changedAt": "2026-02-17T15:45:00+03:00"
}
```

`POST /integration/quality-results` получает `requestId`, `documentId`, `unitId`, `decision`, `sourceEvents`. Коды решения: `GOOD`, `ISOLATE`, `REWORKED_GOOD`, `REWORK`, `SCRAP`. Ответ:

```json
{
  "requestId": "QC-...",
  "result": "OK",
  "receiptId": "GAL-ACK-123",
  "errorCode": null
}
```

`RETRY` означает временный отказ, `REJECT` — окончательный. `requestId` обеспечивает идемпотентность на стороне шлюза.

## Ошибки и проверка перед подключением

Тайм-аут запроса — 5 секунд. Сетевые ошибки, HTTP 429/5xx и квитанции `RETRY` повторяются с нарастающей задержкой, максимум 5 автоматических попыток. HTTP 400/401/403/404 и квитанция `REJECTED`/`REJECT` сохраняются как ошибка для разбора. Неизвестные ID, неверная ревизия, повтор серийного номера или смена содержимого уже полученного заказа отклоняются. Оригинальная квитанция и число попыток видны в журнале.

Перед реальным подключением нужно получить тестовую базу и согласовать: где в ERP хранятся заказ, ревизия и серийный номер; какие документы создаёт решение ОТК; кто владеет справочниками; какие ошибки считаются временными; как шлюз подтверждает уже обработанный ключ. После этого поля и маршруты контракта можно адаптировать без изменения модели качества и интерфейса ОРБИТА.QC.

Проверка локальной реализации: `cd source; pnpm test`. Сквозные тесты поднимают два HTTP-стенда с разными форматами 1С и «Галактики», проверяют авторизацию, сопоставление ID, повтор, квитанцию и сохранение состояния. Это проверка нашего кода и контракта, а не испытание продуктов 1С или «Галактика».
